# Intelligent Document Processing & RAG Platform

> **Status**: 🚧 In Development - Phase 10 complete (persistent conversations over grounded RAG answers; answering is off by default). Versioning and a frontend are not implemented yet.

## Overview

A production-oriented intelligent document processing and Retrieval-Augmented Generation (RAG) platform demonstrating professional-level software engineering practices. This is a portfolio project designed to showcase expertise in backend development, AI/ML integration, and system architecture.

**This is NOT a tutorial project or basic "chat with PDF" application.**

## Problem Statement

Organizations need to extract insights from large document collections. Traditional search provides keyword matching but misses semantic meaning. Pure LLM approaches hallucinate and lack grounding. This platform combines:

- **Semantic understanding** via vector embeddings
- **Precise retrieval** through hybrid search
- **Grounded generation** with citation-backed RAG
- **Quality measurement** through systematic evaluation

## Key Features

### Implemented

**Phase 10 (persistent conversations)**: `/api/v1/conversations` stores user-owned conversations and their messages. `POST /api/v1/conversations/{id}/messages` asks a question inside a conversation: the question is stored first, the answer is generated by the Phase 9 pipeline with the last few exchanges offered as untrusted, bounded, delimited context (never as evidence; citations are validated against this turn's retrieved passages only) and then stored with citation references. Ownership is enforced by the database (composite foreign key), one question is answered at a time per conversation, an optional `Idempotency-Key` makes retries safe (no duplicate question or answer), a failed question is kept and can be retried, and an interrupted request is recovered. Titles are normalised and built without a model call. Deleting a conversation removes its messages; deleting a document removes its name from stored citations. See the [API specification](docs/05_API_SPECIFICATION.md) and decisions DEC-063 to DEC-067 in the [decision log](docs/18_DECISION_LOG.md).

**Phase 9 (grounded answers)**: `POST /api/v1/rag/answer` retrieves from the caller's own documents (hybrid or semantic, optionally reranked), shows a bounded set of passages to a configurable language model (a local Ollama server by default, or any OpenAI-compatible endpoint) and returns an answer whose sentences cite `[S1]`-style sources. Citations are built from database records of the sources actually shown, never from the model's words; labels the model invented are removed, and sentences with a quotation, number or identifier that is not in the cited sources are dropped. If the documents do not answer the question the response says so (`insufficient_evidence`) instead of guessing, and provider failures are explicit errors, never an invented answer. Off by default (`RAG_ENABLED=false`). Retrieved text is treated as untrusted, but no prompt can fully prevent a model from being misled by it (see the security notes). On the bundled 48-question synthetic evaluation the default local model answered 97% of the answerable questions, abstained on all 10 unanswerable ones and produced valid, database-matching citations every time; the dataset is small and author-written (see below).

**Phase 8 (optional reranking)**: `POST /api/v1/search/hybrid` accepts `"rerank": true` to re-score the best candidates with a multilingual cross-encoder (`BAAI/bge-reranker-v2-m3`, pinned revision, safetensors only, no remote code). It is off by default (`RERANK_ENABLED=false`): nothing is downloaded or loaded unless enabled, and without the flag every response is unchanged. Each reranked result carries its position before reranking, the raw model score (not a probability) and whether its text was truncated; if reranking cannot run, the hybrid order is kept and the response says so. On the bundled synthetic evaluation it improved hybrid MRR from 0.931 to 0.981 at a cost of about 1 s of CPU time and 2.3 GB of memory for 10 candidates; the evaluation is small and the model was chosen on it, so treat this as encouraging, not proven (see below).

**Phase 7 (hybrid retrieval)**: `POST /api/v1/search/hybrid` runs the vector retriever and a PostgreSQL full-text retriever and fuses their rankings with Reciprocal Rank Fusion. Exact words, identifiers (`ERR-4721`) and quoted phrases are found even when the embedding model misses them; each result reports its rank in each retriever; if one retriever fails the other still answers. Lexical matching is exact (no stemming: PostgreSQL has no Bengali dictionary), terms are weighted by rarity inside the caller's own documents, and every query is owner-scoped. On the bundled synthetic evaluation hybrid retrieval did **not** beat semantic search overall (MRR 0.931 against 0.940): it won where exact words or phrases matter and lost on some paraphrase and cross-language queries (see below).
Infrastructure, authentication, secure document management, asynchronous text extraction, structure-aware chunking, multilingual embeddings and owner-scoped semantic search; documents are processed into traceable chunks and vectors that can be searched in Bangla, English and mixed text, but no answers are generated yet (no hybrid search, reranking or RAG).

- Local multilingual embeddings (`intfloat/multilingual-e5-small`: 384 dimensions, MIT, 94 documented languages including Bengali, CPU-friendly, about 0.5 GB), behind a provider interface; the model revision is pinned, weights load from safetensors only, and nothing is downloaded into the image
- A versioned vector store in PostgreSQL/pgvector (cosine distance): every vector records the exact model configuration it came from, belongs to a chunk of the same document and to that document's owner (enforced by foreign keys), and a model change requires an explicit re-index instead of silently mixing vectors
- A dedicated embedding worker with batched, idempotent, time-bounded jobs, crash recovery and retries; `ready` now means *searchable* (every chunk has a vector)
- `POST /api/v1/search/semantic`: authenticated, rate-limited, owner-scoped search returning chunk text with page, heading, section and score; no user can reach another user's documents
- A small version-controlled evaluation dataset (Bangla, English, mixed, cross-lingual, confusable and unanswerable queries) with Recall@k, MRR, nDCG@k and latency/throughput measurement

- Deterministic, versioned chunking that never crosses a page or heading boundary: each chunk is an exact slice of its source with page number, heading path and character offsets, bounded in size, with overlap only inside oversized paragraphs
- Bangla-safe splitting (Bengali danda sentence ends, no cut inside a conjunct or ZWJ/ZWNJ sequence), Markdown tables and code fences kept whole, idempotent re-chunking and a `chunked` status that keeps `ready` reserved for searchable documents
- `GET /api/v1/documents/{id}/chunks` for owner-scoped inspection of how a document was split

- Background processing (Celery + Redis) of PDF, DOCX, TXT and Markdown into normalised text with page and heading locations
- Bangla, English and mixed-script documents are preserved (Unicode-safe normalisation, ZWJ/ZWNJ kept, no translation)
- Classified, safe failure reasons, bounded retries, manual retry, and automatic recovery of stuck work

- Upload PDF, DOCX, TXT and Markdown with content validation, checksums and per-user duplicate detection
- Collections, filtered and paginated listing, metadata, streaming download and deletion, all owner-scoped

- Registration, login, refresh-token rotation with reuse detection, logout and `GET /api/v1/auth/me`
- Role-based access control (user, admin) enforced server-side; rate-limited auth endpoints

- FastAPI service with liveness/readiness health endpoints and versioned `/api/v1` routing
- PostgreSQL 16 + pgvector, Redis and a Celery worker, all running under Docker Compose with health checks
- Alembic migrations, structured JSON logging with request IDs, consistent error responses
- React + TypeScript + Vite shell that displays backend readiness
- Test, lint, type-check and CI foundations

## Quick Start

Prerequisites: Docker Desktop (Compose v2). Nothing else is needed to run the stack.

```bash
git clone https://github.com/Jobayer-hasan-rifat/Rag.git
cd Rag

# 1. Create your local environment file and replace the placeholder secrets
cp .env.example .env

# 2. Build and start everything (migrations run automatically)
docker compose up -d --build

# 3. Check status; every service should become "healthy"
docker compose ps
```

| Service | URL |
|---------|-----|
| Frontend | http://localhost:5173 |
| API docs (Swagger) | http://localhost:8000/docs |
| Readiness probe | http://localhost:8000/health/ready |

**First start and the embedding model.** The `embedding_worker` service downloads the embedding model (about 0.5 GB of weights, pinned to a commit hash) into the shared `model_cache` volume the first time it starts, which takes about a minute on a normal connection; documents wait in `chunked` until it is ready. Everything runs on the CPU (the Docker image uses the CPU build of PyTorch); a GPU is optional (`EMBEDDING_DEVICE=auto` uses CUDA or Apple MPS when present). The embedding worker uses about 0.9 GB of memory with the default model (limit 3 GB) and the API loads its own copy for query embedding on the first search. To fetch the model ahead of time: `docker compose run --rm embedding_worker python -m app.embeddings.download`. Changing `EMBEDDING_MODEL`, its revision or the prefixes means re-embedding: run `docker compose exec embedding_worker celery -A app.workers.celery_app:celery_app call app.workers.embedding_tasks.reindex_embeddings`. All settings are listed in `.env.example`.

Try a search once a document is `ready` (replace the token):

```bash
curl -s -X POST http://localhost:8000/api/v1/search/semantic \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"query": "ইলিশ ধরা কবে নিষিদ্ধ?", "top_k": 5}'
```

`score` is the cosine similarity between query and chunk (a ranking signal, not a probability); see the [API specification](docs/05_API_SPECIFICATION.md).

PostgreSQL and Redis are published on `127.0.0.1` only. If a host port is taken (for example Windows reserves 6379 on some machines), change `POSTGRES_HOST_PORT` / `REDIS_HOST_PORT` in `.env`.

## Evaluation

This platform includes systematic evaluation of RAG quality:

### Retrieval Metrics
- Recall@K, Precision@K, Hit@K, MRR

### Generation Metrics
- Answer relevance, groundedness, factual consistency

### Citation Metrics
- Citation precision, recall, correctness

*The full RAG evaluation framework (generation and citation metrics) is planned.*

### Retrieval evaluation (implemented in Phase 6)

`backend/evaluation/` holds a small synthetic dataset (48 passages in English, Bangla and mixed documents; 52 queries including cross-lingual, confusable-wording, punctuation/Unicode and unanswerable ones), metric code (Recall@k, MRR, nDCG@k, answerability AUROC) and runners: `python -m evaluation.retrieval_eval --mode database` evaluates the real pipeline end to end; `python -m evaluation.compare_models` compares candidate models. Measured with the default model on CPU:

| Metric | Value |
|--------|------:|
| Recall@1 / @3 / @10 | 0.891 / 1.000 / 1.000 |
| MRR@10 / nDCG@10 | 0.942 / 0.957 |
| Bangla queries (12) Recall@1 / @3 | 0.917 / 1.000 |
| Cross-lingual queries (4) Recall@1 | 0.750 |

### Hybrid retrieval evaluation (Phase 7)

`python -m evaluation.hybrid_eval` loads the Phase 6 dataset plus a lexical companion (`evaluation/retrieval_lexical/`: identifiers, quoted phrases, names, Bangla inflection, paraphrase and unanswerable queries; 72 passages and 87 queries in all, 77 answerable) into PostgreSQL, embeds them with the real model and answers every query three ways through the real service. Same machine as above.

| Retrieval | Recall@1 | Recall@10 | MRR@10 | nDCG@10 |
|-----------|---------:|----------:|-------:|--------:|
| Dense only | 0.896 | 1.000 | 0.940 | 0.955 |
| Lexical only | 0.805 | 0.857 | 0.831 | 0.838 |
| Hybrid (RRF, k=60, equal weights) | 0.896 | 1.000 | 0.931 | 0.948 |
| Hybrid on the lexical companion alone (31 queries) | 0.968 | 1.000 | 0.984 | 0.988 |
| Dense on the lexical companion alone | 0.935 | 1.000 | 0.953 | 0.964 |

Hybrid retrieval was better for quoted phrases (MRR 1.00 against 0.63 for dense) and Bangla questions with exact words (1.00 against 0.96), equal for identifiers and mixed-script queries, and worse for cross-language queries (0.50 against 0.71) and confusable wording (0.61 against 0.88): a lexical match on the wrong passage can outrank a correct semantic one. The default fusion settings were not tuned (a dense-heavy weighting looked slightly better on this data but the data is too small to justify it). Caveats: 77 answerable queries; written by the author; the function-word filter was added after the first run exposed noisy lexical matches (hybrid MRR was 0.874 before it; both result files are kept in `evaluation/results/`). Equal Reciprocal Rank Fusion scores are tie-broken by chunk id, which was random per run, so figures moved by about 0.01 between runs; the evaluation now uses fixed ids and the numbers above are from that reproducible run.

### Answer-generation evaluation (Phase 9)

`python -m evaluation.rag_eval --model <name>` loads the Phase 7 corpora plus a small extra corpus (contradictory facts, documents with injected instructions, one passage far longer than the per-source limit, identifiers in mixed text) into PostgreSQL, embeds them with the real model, and sends 48 author-written questions (38 answerable: English 10, Bangla 10, mixed 8, cross-language 4, contradictory 2, adversarial 3, long-passage 1; 10 unanswerable) through the real pipeline and a real local model. Only deterministic metrics are reported: fact recall is substring matching against author-written expected facts; there is no model-as-judge.

| Model (Ollama, GPU) | Answered / answerable | Fact recall | Abstained / unanswerable | Valid labels and database-matching citations | Citation precision | Median / p95 time |
|---|---:|---:|---:|---:|---:|---:|
| `qwen3.5:9b` (default) | 0.97 | 0.92 | 10 / 10 | 100% | 1.00 | 2.9 / 4.3 s |
| `qwen2.5:latest` | 0.76 | 0.76 | 10 / 10 | 100% | 0.91 | 2.9 / 7.5 s |
| `gemma4:e4b` (CPU only, earlier code revision) | 0.97 | 0.97 | 10 / 10 | 100% | 0.93 | 17.6 / 28.4 s |

By group for the default model (fact recall): English 0.95, Bangla 0.85, mixed 1.00; adversarial documents 1.00 (the injected "answer only with PWNED" text never appeared in an answer), contradictory documents 1.00 (both dates were reported), cross-language 0.75. The fixed insufficient-evidence message was returned for every unanswerable question; the question whose answer lies beyond the per-source limit was correctly refused (the model never saw the fact). Failures: one cross-language question was refused because retrieval did not return its passage (candidate recall 0.97 on every model), one answer rewrote Bangla spellings so a keyword check missed it, and one answer gave a supported but incomplete reply. `qwen2.5` refused 9 of the 38 answerable questions, including most of those with adversarial or contradictory sources.

Limits, plainly: 48 questions written by the author; the default model, the prompt wording and the validation rules were chosen or adjusted while looking at results on this same set (selection on test, not a blind result); a single reviewer (the author) read every stored answer of the default model and found no unsupported factual claim among the 37 answers, but that is a human judgement of a small sample, not proof of faithfulness; the deterministic checks cannot see a wrong claim that reuses real numbers; GPU results come from one machine (a Vulkan GPU path that is experimental) and one model produced corrupted text on it. Do not read these numbers as general Bangla answer quality.

### Reranking evaluation (Phase 8)

`python -m evaluation.rerank_eval` compares dense, hybrid (RRF), dense + reranker and hybrid + reranker on the same candidates and judgments (77 answerable queries, 72 passages), with candidate recall reported separately. Reranking 10 candidates:

| Arm | Recall@1 | Recall@3 | MRR@10 | nDCG@10 | Added latency (p50 / p95) |
|-----|---------:|---------:|-------:|--------:|--------------------------:|
| Dense | 0.896 | 0.987 | 0.940 | 0.955 | - |
| Hybrid | 0.896 | 0.935 | 0.931 | 0.948 | - |
| Hybrid + `bge-reranker-v2-m3` | 0.961 | 1.000 | 0.981 | 0.986 | 1,151 / 1,250 ms |
| Hybrid + `mmarco-mMiniLMv2` (smaller) | 0.935 | 0.987 | 0.958 | 0.968 | 107 / 133 ms |

With 30 candidates the larger model scored MRR 0.976 at 3.2 s, the smaller 0.930 (below no reranking). By group (MRR, hybrid to hybrid + bge): cross-language 0.50 to 1.00, confusable wording 0.61 to 1.00, mixed Bangla-English 0.95 to 1.00, punctuation/Unicode 0.88 to 1.00; unchanged for Bangla, identifiers, rare terms and quoted phrases; slightly lower for plain English (1.00 to 0.95) and Bangla inflection (1.00 to 0.83, 3 queries). The smaller model hurt paraphrase queries (0.94 to 0.74) and the lexical companion set. Dense + reranking and hybrid + reranking were identical here: the corpus is so small that both candidate sets contain the answer and the reranker's order decides everything, so this dataset cannot say which retriever should feed it.

Limits: candidate recall was 1.0 everywhere (72 passages, 10 candidates), so the evaluation cannot show what reranking costs when retrieval misses; the dataset is author-written and small; the model, the candidate count and the default settings were chosen on this same set; a separate 24-passage, 30-query held-out set was run once and showed no harm but could not show improvement (dense retrieval already scored 1.000). The numbers are not evidence of a general Bangla retrieval improvement. Latency was measured on a 6-thread desktop CPU in process; over HTTP in Docker, reranking 6 candidates took p50 499 ms against 31 ms for plain hybrid search, and the first reranked request before the model was loaded took 7 s.

The same dataset shows why the embedding model was chosen: a multilingual model that does not list Bengali among its languages reached Bangla Recall@1 of 0.42 against 0.92 here (see DEC-037 in the [decision log](docs/18_DECISION_LOG.md)). **Read these numbers carefully:** the dataset is small (one query is about 2 points), synthetic, written by one author, uses short passages, and the model was selected on it, so the results show that the pipeline separates these passages, not that Bangla retrieval is strong in general. A larger evaluation on real documents is planned.

## Security

Security is a first-class concern in this project:

- **Authentication**: short-lived JWT access tokens, rotating hashed refresh tokens with reuse detection, bcrypt password hashing, Redis-backed rate limiting
- **Authorization**: Role-based access control (RBAC)
- **Input Validation**: Pydantic schemas, file validation
- **Document Security**: all uploads treated as untrusted: size caps, signature and structure checks, generated storage keys, attachment-only downloads, owner-scoped access
- **Secrets Management**: Environment variables, no hardcoded credentials

See the [Security Overview](docs/06_SECURITY.md) for details.

Persisting chunks in batches of 1,000 rows took 74 ms for 1,000 chunks and 676 ms for 10,000, about 9-10x faster than row-by-row inserts (652 ms and 6.7 s). Chunking is a small fraction of end-to-end processing time; extraction dominates.

Chunk quality is measured on a seeded synthetic corpus (`python -m benchmarks.chunking_eval`): on all ten corpus cases every chunk is within the size limit and an exact slice of its source, all non-whitespace text is covered, no chunk starts or ends inside a grapheme cluster, and output is deterministic; prose chunks end on a sentence or paragraph boundary in 100% of cases with a mean size of roughly 65-85% of the limit. This is a structural evaluation of the splitter, not a retrieval-quality measurement; retrieval quality is evaluated in a later phase.

| Vector search through the real schema, 2,500 of 50,000 vectors (p50) | 6.6 ms |
| Vector search, one user owning 50,000 vectors (p50) | 23.7 ms |
| Search over HTTP in the Docker stack (4 documents, p50 / p95) | 26 / 29 ms |

On CPU, small batches were fastest (batch 4-8; throughput falls as the batch grows), so the default batch size is 8. **GPU throughput was not measured: no GPU was available.** Search is exact by default (no ANN index): per-user exact scans matched an HNSW index on speed with perfect recall in the multi-user case (details and thresholds in DEC-039). Numbers come from one desktop machine and synthetic vectors.

Hybrid search baseline (Phase 7; `python -m benchmarks.hybrid_search_baseline`, real schema, repositories timed without the model, synthetic Zipf-like text, 20 users):

| Chunks in table | Dense p50 / p95 | Lexical p50 / p95 | Whole hybrid p50 / p95 |
|----------------:|----------------:|------------------:|-----------------------:|
| 10,000 | 2.5 / 3.0 ms | 2.8 / 6.5 ms | 6.7 / 10.6 ms |
| 100,000 | 17.4 / 22.4 ms | 5.1 / 23.8 ms | 24.4 / 44.4 ms |

Hybrid over HTTP in the Docker stack (4 documents, real model): p50 28.5 ms, p95 31.1 ms; the first request after a restart loads the model in the API process (about 9 s). The lexical index adds about 11% to the chunk table size.

These exclude storage reads, database writes (except the chunk insert figures above) and queueing. Remaining benchmarks are planned for Phase 14:

- Document parsing throughput
- Embedding generation latency
- Search latency (semantic, keyword, hybrid)
- RAG pipeline latency
- End-to-end query latency
